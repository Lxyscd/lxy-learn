第01节 · 为什么需要异步？

1.1 从一个生活例子说起

想象你去食堂吃饭：

� 同步模式（Synchronous） 你走到窗口对阿姨说：「我要一份红烧肉盖饭」。然后你就站在窗口等着， 一直等、一直等……5 分钟后阿姨把饭递给你，你才端着饭去座位吃。 这 5 分钟里，你啥也干不了——不能玩手机、不能找座位、不能买饮料。你被阻塞住了。
⚡ 异步模式（Asynchronous） 你走到窗口对阿姨说：「我要一份红烧肉盖饭」，阿姨给你一个取餐号码牌。 你拿着号码牌：去找座位 → 买瓶饮料 → 刷了会儿手机 → 听到「请 37 号取餐！」→ 去拿饭。 做饭的这几分钟里，你同时做了 N 件事。你没有被阻塞。

1.2 在代码中意味着什么？

JavaScript 是单线程的（同一时间只能做一件事），所以如果代码「同步」执行遇到耗时操作，就会阻塞后面的所有代码：

// 假设这是一个"耗时3秒"的操作（比如网络请求）
function 耗时操作() {
  const start = Date.now();
  while (Date.now() - start < 3000) {} // 空转3秒，模拟阻塞
  return '数据';
}

console.log('1. 开始');
const result = 耗时操作();           // 卡在这里 3 秒！
console.log('2. 拿到结果：', result);  // 3秒后才执行
console.log('3. 后面的代码');       // 也要等3秒后才执行

/* 输出：
  1. 开始
  （卡3秒...）
  2. 拿到结果：数据
  3. 后面的代码
*/
⚠️ 在网页中的致命后果 如果 JS 是同步阻塞的，那么当网络请求慢的时候——整个页面会「卡死」， 用户点击按钮没反应、页面滚动不了、动画全部停止。用户体验极差。 所以 JS 必须支持异步。

1.3 异步版本的对比

// 异步版本：不会阻塞后面的代码
console.log('1. 开始');
耗时操作Async('数据');         // 发起请求，但不等待结果
console.log('2. 后面的代码');       // 立刻执行！不等待！

/* 输出：
  1. 开始
  2. 后面的代码     ← 注意：这里立刻打印了，没有等3秒
  （3秒后...）
  数据准备好了      ← 异步回调此时才触发
*/

1.4 JS 中常见的异步场景

场景例子耗时
网络请求fetch('/api/user')几百毫秒~几秒
定时器setTimeout / setInterval指定时间
文件读取fs.readFile()（Node.js）取决于文件大小
DOM 事件点击、滚动、输入等事件回调用户触发时
数据库查询数据库操作（Node.js 后端）几十毫秒~几秒
📌 本节总结 异步 = 发起一个操作后不等待结果，继续执行后面的代码。 等操作完成后，通过某种机制（回调 / Promise / async-await）拿到结果。 JS 作为浏览器脚本语言，异步是其核心能力——没有异步就没有现代 Web 应用。

第02节 · JS 为什么是单线程？

你可能会问：「为什么不把 JS 设计成多线程？这样不就不用搞异步了吗？」

2.1 历史原因

1995 年 Brendan Eich 用 10 天创造了 JS，那时候的用途非常简单——表单校验、简单动画。根本不需要多线程，单线程就够了。

2.2 多线程的噩梦——DOM 操作

假设 JS 是多线程的，会发生什么？

线程 A：正在读取 <div id="box"> 的内容 线程 B：正在删除 <div id="box"> 结果：线程 A 读到了一个「已经被删除的节点」→ � Bug！

如果 JS 有多线程，操作 DOM 就需要加锁、同步，代码复杂度爆炸。所以 JS 选择单线程 + 异步来避免线程竞争问题。

2.3 单线程的代价与解法

❌ 单线程的代价

同一时间只能执行一个任务
遇到耗时操作会阻塞后面所有代码
页面会"假死"

✅ 异步来救场

耗时操作丢给"后台"（浏览器 API）
主线程继续执行后续代码
后台完成后通知主线程

2.4 浏览器中的「多线程」

虽然 JS 引擎是单线程的，但浏览器不是单线程的。浏览器为 JS 提供了很多「Web API」：

Web API在哪个线程执行完成后通知方式
setTimeout / setInterval计时器线程回调放入任务队列
fetch / XMLHttpRequest网络线程回调放入任务队列
DOM 事件（click / scroll 等）事件线程回调放入任务队列

这些 API 在浏览器的其他线程中执行，执行完毕后会把回调函数放到一个「任务队列」里。JS 主线程执行完毕后，会去任务队列里取回调执行。这就是 Event Loop 的基本原理。

第03节 · 事件循环 Event Loop

Event Loop（事件循环）是 JS 异步机制的核心原理。理解了这个，你就理解了异步的本质。

3.1 JS 引擎的三大核心组件

�─────────────────────────────────────────────────────────┐ │ JS 引擎（V8 等） │ │ │ │ �──────────────┐ ┌──────────────┐ ┌───────────────� │ │ │ 调用栈 │ │ 堆 Heap │ │ 任务队列 │ │ │ │ Call Stack │ │ │ │ Message Queue │ │ │ │ │ │ 存放对象 │ │ │ │ │ │ 存放正在执行 │ │ 和数据 │ │ 存放异步回调 │ │ │ │ 的函数调用 │ │ │ │ 等待执行 │ │ │ │ │ │ │ │ │ │ │ │ 一次只能有 │ │ │ │ 先进先出 │ │ │ │ 一个在执行 │ │ │ │ (FIFO) │ │ │ └──────────────┘ └──────────────┘ └───────────────┘ │ │ │ └─────────────────────────────────────────────────────────┘ �─────────────────────────────────────────────────────────┐ │ Web APIs（浏览器提供） │ │ │ │ setTimeout │ fetch │ DOM 事件 │ XMLHttpRequest │ │ │ │ 这些 API 执行完毕后，把回调放入任务队列 │ └─────────────────────────────────────────────────────────┘

3.2 Event Loop 的执行规则

1
JS 引擎按顺序执行所有同步代码（放进 Call Stack）
遇到函数调用就入栈，函数返回就出栈
2
遇到异步操作（setTimeout、fetch 等）
交给 Web API 去执行，主线程继续往下走
3
Web API 执行完毕后，把回调放进任务队列
等待被 JS 引擎取走执行
4
Call Stack 空了（同步代码全部执行完）
Event Loop 开始工作
5
Event Loop 从任务队列取一个回调 → 放进 Call Stack → 执行
重复此过程（循环）→ 这就是 "Loop"

3.3 一个关键认知

⚠️ 重点：setTimeout 的回调不是「到了时间就执行」

setTimeout(fn, 0) 的意思是：0 毫秒后，把 fn 放进任务队列。 但 fn 能不能立刻执行，取决于 Call Stack 是否为空。 如果同步代码还没执行完，fn 就得在队列里等着。

3.4 用一个完整的例子来理解

console.log('1');               // 同步 → 立刻执行

setTimeout(() => {
  console.log('2');           // 异步 → 放入任务队列，等栈空了再执行
}, 0);

console.log('3');               // 同步 → 立刻执行（不等待 setTimeout）

/* 请问输出顺序是？ */
// 答案：1 → 3 → 2

很多人以为 setTimeout(fn, 0) 会第二个执行，实际上它是最后一个——因为它是异步的。

📌 本节总结 JS 单线程 + Event Loop = 用「异步回调」模拟「同时做多件事」。 Web API 在后台执行耗时操作，主线程不被阻塞。 操作完成后回调进入任务队列，等 Call Stack 空了才被执行。 记住一句话：JS 永远先执行完所有同步代码，才会执行异步回调。

第04节 · 回调函数 Callback

4.1 什么是回调？

回调就是：把一个函数作为参数传给另一个函数，等某个条件满足时再调用这个函数。

// 最简单的回调例子
function 做饭(菜名, 做好了告诉我) {   // ← "做好了告诉我" 就是一个回调函数
  console.log(`正在做${菜名}...`);
  setTimeout(() => {
    做好了告诉我(菜名);  // ← 3秒后"调用"回调，通知调用者
  }, 3000);
}

// 使用：传入一个函数作为"回调"
做饭('红烧肉', (菜名) => {
  console.log(`${菜名}好了！开吃！`);
});

console.log('去做别的事情...');  // 不等待，立刻执行

/* 输出：
  正在做红烧肉...
  去做别的事情...     ← 注意：不等待，先执行了这行
  （3秒后...）
  红烧肉好了！开吃！   ← 回调被"调用"了
*/

4.2 回调是 JS 异步的基石

几乎所有异步 API 都用回调：

// 1. setTimeout 的回调
setTimeout(() => console.log('1秒后执行'), 1000);

// 2. DOM 事件的回调
btn.addEventListener('click', () => console.log('按钮被点击了'));

// 3. fetch 的回调（旧写法）
fetch('/api/user')
  .then(response => response.json())
  .then(data => console.log(data));

// 4. 数组方法的回调
[1, 2, 3].map(n => n * 2);
arr.filter(n => n > 5);
📌 本节总结 回调 = 你给别人的函数，别人到时候「回调」给你。 回调是最基础的异步模式，简单直接。 但当多个异步操作需要按顺序执行时，回调会变成噩梦……

第05节 · 回调地狱 Callback Hell

5.1 什么是回调地狱？

当多个异步操作有依赖关系（必须等前一个完成才能执行下一个）时，回调会一层套一层：

// 场景：先获取用户 → 用用户ID获取订单 → 用订单ID获取商品详情
// （这是前端最常见的「串行请求」场景）

获取用户('张三', (user) => {                    // 第1层
  console.log('用户：', user.name);
  获取订单(user.id, (orders) => {              // 第2层
    console.log('订单：', orders);
    获取商品(orders[0].id, (product) => {   // 第3层
      console.log('商品：', product);
      获取评价(product.id, (reviews) => {   // 第4层 💀
        console.log('评价：', reviews);
        // 第5层、第6层... 无限嵌套下去
      });
    });
  });
});
💀 回调地狱的四大罪状
1. 代码横向发展——向右缩进越来越多，像阶梯一样
2. 难以阅读——逻辑嵌套太深，不知道哪个 then 对应哪个回调
3. 难以维护——想在中间加一步？拆开重构吧
4. 错误处理困难——每一层都要单独 try/catch（回调里还没 try/catch）

5.2 回调地狱的解决方案——Promise

为了解决回调地狱，ES6 引入了 Promise。它让异步代码可以链式调用，从横向发展变回纵向书写：

// 回调地狱版（上一段的代码）
获取用户('张三', (user) => {
  获取订单(user.id, (orders) => {
    获取商品(orders[0].id, (product) => {
      获取评价(product.id, (reviews) => {
        // 第5层了... 💀
      });
    });
  });
});

// Promise 链式调用版（纵向书写，清晰！）
获取用户Promise('张三')
  .then(user => 获取订单Promise(user.id))
  .then(orders => 获取商品Promise(orders[0].id))
  .then(product => 获取评价Promise(product.id))
  .then(reviews => console.log('评价：', reviews))
  .catch(err => console.error('任何一步出错都会到这里：', err));
📌 本节总结 回调本身没问题，但「回调里套回调」会导致代码失控。 Promise 的诞生就是为了解决这个问题——让异步代码扁平化。

第06节 · Promise 是什么？

6.1 生活类比：一张外卖订单

🍔 把 Promise 想象成一张外卖订单

你打开美团外卖点了一份黄焖鸡 → 系统给你生成了一张订单（Promise）

这张订单有三种可能：
• 等待中（pending）—— 骑手正在取餐、正在路上
• 已送达（fulfilled）—— 你拿到了饭，可以吃了 �
• 订单取消（rejected）—— 商家不做了，退款给你 �

订单一旦「送达」就不可能再变成「等待中」。状态是不可逆的。

你拿到订单后可以做什么？
• then：收到饭后干什么（比如浇汁儿、开吃）
• catch：饭没送到怎么办（申请退款）
• finally：无论收没收到都要做的事（擦桌子）

6.2 Promise 的本质

Promise 是一个对象，它代表一个异步操作的最终结果（成功或失败）。

Promise 的核心价值：用对象来代表一个「未来才会知道的结果」。

// 不用 Promise：你现在必须等结果
const result = fetchSync('/api/user');  // 卡在这里，等3秒
console.log(result);

// 用 Promise：你立刻拿到一个"承诺"（还没拿到数据）
const promise = fetch('/api/user');  // 立刻返回！不等待！
console.log(promise);                  // Promise { <pending> }
promise.then(data => console.log(data));  // 等拿到数据后再执行
📌 本节总结 Promise = 一个对象，代表「未来某个时刻才会有」的结果。 它现在是 pending，将来会变成 fulfilled 或 rejected。 你通过 .then() 注册「成功后做什么」，通过 .catch() 注册「失败后做什么」。

第07节 · Promise 的三种状态

7.1 状态详解

状态英文含义触发条件
进行中pending操作还没完成，正在等待Promise 刚创建时
已成功fulfilled / resolved操作成功完成调用 resolve(value)
已失败rejected操作失败调用 reject(reason) 或抛出异常

7.2 状态转换规则（极其重要！）

�──────────┐ │ pending │ ← Promise 创建后的初始状态 └────�─────┘ │ ├──────────────┬──────────────� │ │ │ ▼ │ ▼ ┌──────────┐ │ �──────────� │fulfilled │ │ │ rejected │ └──────────┘ │ └──────────┘ │ │ │ │ │ │ ▼ ▼ ▼ ✅ 调用 .then() ❌ 不会变 ✅ 调用 .catch() 的第二个参数 或 .then() 的 处理 fulfilled 第二个参数
⚠️ 核心规则：状态只能改变一次！

从 pending → fulfilled 或者 pending → rejected，二选一，不可逆。
一旦变成 fulfilled，再调用 reject() 也不会变成 rejected（会被忽略）。
同理，一旦变成 rejected，再调用 resolve() 也没用。

7.3 代码验证

const p = new Promise((resolve, reject) => {
  resolve('第一次调用');
  reject('第二次调用');   // ← 被忽略！因为已经 fulfilled 了
  resolve('第三次调用');   // ← 也被忽略
});

p.then(
  value => console.log('成功：', value),   // 输出：成功：第一次调用
  reason => console.log('失败：', reason) // 永远不会执行
);
📌 本节总结 pending → fulfilled 或 pending → rejected，只能变一次，不可逆。 这个特性保证了异步操作的确定性——结果要么成功要么失败，不会变来变去。

第08节 · 创建 Promise

8.1 new Promise(executor)

Promise 通过 new Promise() 创建。构造函数接收一个参数：executor（执行器函数）。

const promise = new Promise((resolve, reject) => {
  // executor 函数：在这里写异步逻辑
  // resolve: 成功的回调（把 pending 变成 fulfilled）
  // reject:  失败的回调（把 pending 变成 rejected）
});

8.2 一个完整的模拟异步操作例子

// 模拟一个"2秒后返回用户数据"的异步操作
function 获取用户数据(userId) {
  return new Promise((resolve, reject) => {
    console.log(`正在请求用户 ${userId}...`);

    setTimeout(() => {
      // 模拟 80% 成功率
      if (Math.random() > 0.2) {
        // 成功！调用 resolve，把 Promise 状态从 pending 变成 fulfilled
        resolve({
          id: userId,
          name: '张三',
          age: 25
        });
      } else {
        // 失败！调用 reject，把 Promise 状态从 pending 变成 rejected
        reject(new Error('网络错误，请重试'));
      }
    }, 2000);
  });
};
⚠️ 关于 executor 函数的执行时机
executor 函数是同步执行的！它会在 new Promise() 时立刻执行。 只有 executor 里面的异步操作（如 setTimeout）才会异步完成。 
// 验证：executor 是同步执行的
console.log('1. 开始');

const p = new Promise((resolve, reject) => {
  console.log('2. executor 执行（同步！）');
  setTimeout(() => {
    console.log('4. setTimeout 回调（异步）');
    resolve('成功');
  }, 1000);
});

console.log('3. new Promise 之后');

p.then(value => console.log('5. then 回调：', value));

/* 输出顺序：1 → 2 → 3 → (等1秒) → 4 → 5 */

8.3 把任意回调式 API 包装成 Promise（Promisify）

实际项目中有很多老 API 用的是回调风格（比如 Node.js 的 fs.readFile），我们可以用 new Promise 把它们包装成 Promise：

// 把 setTimeout 包装成一个返回 Promise 的函数
function 延迟(ms) {
  return new Promise(resolve => setTimeout(resolve, ms));
}

// 使用：配合 async/await 用就非常优雅
async function main() {
  console.log('开始');
  await 延迟(1000); // 等1秒
  console.log('1秒后');
  await 延迟(1000); // 再等1秒
  console.log('2秒后');
}
📌 本节总结 new Promise((resolve, reject) => { ... })： executor 同步执行，在里面写异步逻辑。 成功时调用 resolve(value)，失败时调用 reject(reason)。 这个模式是所有 Promise 的基础。

第09节 · 消费 Promise · then / catch / finally

创建了一个 Promise 之后，我们需要「消费」它——也就是注册成功/失败后的回调。

9.1 .then() 方法

// .then() 接收两个参数（都是函数）：
// 第一个参数：Promise 变成 fulfilled 时调用
// 第二个参数：Promise 变成 rejected 时调用（可选）

promise.then(
  (value) => {
    console.log('成功！值是：', value);
  },
  (reason) => {
    console.log('失败！原因是：', reason);
  }
);

9.2 .catch() 方法

// .catch(fn) 等价于 .then(null, fn)
// 只处理 rejected 的情况

promise
  .then(value => console.log('成功：', value))
  .catch(err => console.log('失败：', err));

// ⚠️ 注意：.catch() 也会捕获前面 .then() 中抛出的异常！
promise
  .then(value => {
    throw new Error('then 里面出错了！');
  })
  .catch(err => console.log('捕获到：', err)); // 能捕获到！

9.3 .finally() 方法

// .finally() 无论成功还是失败都会执行
// 它不接收参数（不知道结果是成功还是失败）
// 用途：关闭 loading、清理资源等

loadData()
  .then(data => console.log('数据：', data))
  .catch(err => console.log('错误：', err))
  .finally(() => {
    hideLoadingSpinner(); // 无论成功失败都要关闭 loading
  });

9.4 三个方法的对比表

方法调用时机参数返回值
.then(onFulfilled, onRejected)fulfilled 或 rejectedvalue / reason新的 Promise（链式的基础）
.catch(onRejected)rejectedreason新的 Promise（链式的基础）
.finally(onFinally)无论成败无新的 Promise（一般不用）
💡 链式的关键 .then()、.catch()、.finally() 都会返回一个新的 Promise。 这就是为什么你可以 .then().then().then() 链式调用。

第10节 · Promise 链式调用（核心！）

链式调用是 Promise 最强大的特性，也是解决回调地狱的关键。但其中 then 里 return 的奥秘，很多人搞不清楚。

10.1 核心规则

.then() 的 return 值决定下一个 .then() 收到什么： return 普通值 → 下一个 .then() 立刻收到这个值 return Promise → 下一个 .then() 等这个 Promise 完成后收到结果 throw Error → 跳过所有后续 .then()，直接进 .catch() 不 return → 下一个 ..then() 收到 undefined

10.2 四种情况逐一演示

情况1：return 普通值

Promise.resolve(1)
  .then(v => {
    console.log(v);  // 1
    return v + 1; // return 普通值 2
  })
  .then(v => {
    console.log(v);  // 2（立刻收到，不用等）
  });

情况2：return Promise（重要！）

Promise.resolve(1)
  .then(v => {
    console.log(v);  // 1
    // return 一个新的 Promise
    return new Promise(resolve => setTimeout(() => resolve(v + 1), 1000));
  })
  .then(v => {
    console.log(v);  // 2（要等上面的 Promise 完成，等1秒）
  });

情况3：throw Error

Promise.resolve(1)
  .then(v => {
    throw new Error('出错了！');
  })
  .then(v => {
    console.log('这行不会执行'); // 被跳过！
  })
  .catch(err => {
    console.log('捕获：', err.message); // 捕获：出错了！
  });

情况4：不 return

Promise.resolve(1)
  .then(v => {
    console.log(v);  // 1
    // 没有 return → 默认 return undefined
  })
  .then(v => {
    console.log(v);  // undefined
  });

10.3 实战：串行请求的经典模式

// 场景：获取用户 → 获取该用户的订单 → 获取第一个订单的商品

fetch('/api/user/1')                    // 第1步：获取用户
  .then(response => response.json())     // 把响应体解析为 JSON
  .then(user => {                      // 第2步：用用户ID获取订单
    return fetch(`/api/orders?userId=${user.id}`);
  })
  .then(response => response.json())     // 把订单响应解析为 JSON
  .then(orders => {                     // 第3步：获取商品
    const firstOrder = orders[0];
    return fetch(`/api/products/${firstOrder.productId}`);
  })
  .then(response => response.json())
  .then(product => {
    console.log('最终商品：', product);
  })
  .catch(err => {                       // 任何一步出错都进这里
    console.error('请求链中出错：', err);
  })
  .finally(() => {
    hideLoading();
  });
� 链式调用的生活类比：流水线作业

每个 .then() 是流水线上的一个工人。 工人做完手里的活儿，把产品（return 值）传给下一个工人。 如果某个工人出了错（throw），整条流水线停掉，转到废品处理（.catch()）。
� 本节总结 .then() 的 return 决定了下一个 .then() 收到什么。 return 普通值 → 立刻传给下一个 then。 return Promise → 等 Promise 完成后传给下一个 then。 throw → 跳过所有 then，直接进 catch。 这就是 Promise 链的全部奥秘！

第11节 · Promise 静态方法大全

Promise 有 4 个静态方法，用来同时处理多个 Promise。这是面试必考、工作必备。

11.1 Promise.all() —— 全部成功才算成功

场景：同时发多个请求，等全部完成后一起处理 Promise.all([请求A, 请求B, 请求C]) 请求A ──→ 结果A ──┐ 请求B ──→ 结果B ──┼──→ .then([结果A, 结果B, 结果C]) 请求C ──→ 结果C ──� ⚠️ 任何一个失败 → 整个 .all() 立刻失败（进 .catch） 
// 场景：页面加载时需要同时获取 3 份数据
async function 加载首页数据() {
  // 三个请求同时发出，不用等前一个完成
  const [user, products, notifications] = await Promise.all([
    fetch('/api/user').then(r => r.json()),
    fetch('/api/products').then(r => r.json()),
    fetch('/api/notifications').then(r => r.json())
  ]);

  console.log(user, products, notifications);
  // 如果任何一个请求失败，整行都不执行，直接进 catch
}

// 错误处理
加载首页数据().catch(err => {
  console.error('某个请求失败了：', err);
});
❌ 不用 Promise.all
const user = await fetch('/api/user');
const products = await fetch('/api/products');
const notes = await fetch('/api/notifications');
// 串行！总耗时 = t1 + t2 + t3
✅ 用 Promise.all
const [user, products, notes] =
  await Promise.all([
    fetch('/api/user'),
    fetch('/api/products'),
    fetch('/api/notifications')
  ]);
// 并发！总耗时 = max(t1, t2, t3)

11.2 Promise.race() —— 谁先完成用谁

场景：多个请求赛跑，谁先完成就用谁的结果 Promise.race([请求A, 请求B, 请求C]) 请求A ──→ 先完成！──→ .then(请求A的结果) 请求B ──→ 还没完成（被忽略） 请求C ──→ 还没完成（被忽略） 
// 实战场景1：超时控制
const 数据请求 = fetch('/api/slow-data');
const 超时 = new Promise((_, reject) =>
  setTimeout(() => reject(new Error('超时！')), 5000)
);

try {
  const result = await Promise.race([数据请求, 超时]);
  // 5秒内返回 → 拿到数据
} catch (err) {
  // 5秒后返回 → 超时错误
}

// 实战场景2：从多个镜像源下载，用最快的
Promise.race([
  fetch('https://mirror1.example.com/data'),
  fetch('https://mirror2.example.com/data'),
  fetch('https://mirror3.example.com/data')
]).then(res => console.log('最快的镜像返回了'));

11.3 Promise.allSettled() —— 等全部完成（不论成败）

场景：不管成功失败，等所有请求都结束后统一处理 Promise.allSettled([请求A, 请求B, 请求C]) 请求A ──→ 成功 ──→ { status: 'fulfilled', value: ... } 请求B ──→ 失败 ──→ { status: 'rejected', reason: ... } 请求C ──→ 成功 ──→ { status: 'fulfilled', value: ... } 
// 场景：批量上传文件，不管哪个失败都要继续
const 上传结果 = await Promise.allSettled([
  fetch('/upload/file1', { method: 'POST', body: file1 }),
  fetch('/upload/file2', { method: 'POST', body: file2 }),
  fetch('/upload/file3', { method: 'POST', body: file3 })
]);

上传结果.forEach((result, i) => {
  if (result.status === 'fulfilled') {
    console.log(`文件${i+1}上传成功`);
  } else {
    console.log(`文件${i+1}上传失败：`, result.reason);
  }
});

11.4 Promise.any() —— 任何一个成功就行（ES2021）

场景：多个请求，只要有一个成功就用它的结果 Promise.any([请求A, 请求B, 请求C]) 请求A ──→ 失败（忽略） 请求B ──→ 成功！──→ .then(请求B的结果) 请求C ──→ 失败（忽略） ⚠️ 全部失败 → .catch(AggregateError)

11.5 四个静态方法对比表

方法什么时候 .then()什么时候 .catch()典型用途

Promise.race任何一个先完成任何一个先失败超时控制

Promise.race：先到先得，常用于超时控制。

Promise.any：有一个成功就行，全部失败才报错。

第12节 · Promise 错误处理机制

12.1 catch 的「冒泡」特性

Promise 的错误会像「冒泡」一样，从链的开始一直向后传递，直到遇到 .catch() 或链的末尾。

// 错误冒泡示例
Promise.resolve()
  .then(() => {
    console.log('第1个 then');
  })
  .then(() => {
    console.log('第2个 then');
    throw new Error('在第2个 then 中出错！'); // ← 错误发生在这里
  })
  .then(() => {
    console.log('第3个 then（不会执行）'); // ← 被跳过
  })
  .catch(err => {
    console.log('捕获到：', err.message); // ← 错误被这里捕获
  })
  .then(() => {
    console.log('第4个 then（会执行！）'); // ← catch 后又恢复了
  });

/* 输出：
  第1个 then
  第2个 then
  捕获到：在第2个 then 中出错！
  第4个 then（会执行！）
*/

12.2 catch 之后链会「恢复」

💡 关键认知 .catch() 也会返回一个新的 Promise。 如果 catch 里没有抛出错误，下一个 .then() 会正常执行。 就像 Java 里 catch 了异常后程序继续运行一样。

12.3 遗漏 catch 的后果

⚠️ 未处理的 Promise 拒绝（Unhandled Promise Rejection）
如果 Promise 链末尾没有 .catch()，当 Promise rejected 时， 浏览器控制台会报 Uncaught (in promise) Error， 在 Node.js 中可能导致进程崩溃。

永远在 Promise 链的末尾加上 .catch()！

12.4 全局兜底（保险做法）

// 浏览器环境：监听所有未处理的 Promise rejection
window.addEventListener('unhandledrejection', event => {
  console.error('未处理的 Promise 错误：', event.reason);
  // 可以上报到监控系统
});

// Node.js 环境
process.on('unhandledRejection', (reason, promise) => {
  console.error('未处理的 Promise 错误：', reason);
});
📌 本节总结 Promise 中的错误会「冒泡」到链末尾。 中间的任何 .catch() 都能捕获它。 catch 之后链会「恢复」，后续 then 正常执行。 永远不要忘记在链末尾加 catch！

第13节 · async / await 基本用法

13.1 一句话总结

� async/await = Promise 的语法糖

Promise 解决了回调地狱，但链式调用多了也不好看（.then().then().then()）。 async/await 让异步代码看起来像同步代码，但本质上还是异步的！

13.2 基本语法

// 普通函数
function getData() {
  return 123;
}

// async 函数：在 function 前面加 async
async function getData() {
  return 123; // 等价于 return Promise.resolve(123)
}

// await：在 async 函数内部，等待一个 Promise 完成
async function main() {
  // await 会"暂停"在这里，直到 fetch 完成
  // 但注意：它不会阻塞主线程！其他代码（比如 UI 渲染）照常进行
  const response = await fetch('/api/user');
  const user = await response.json();
  console.log(user);
}

13.3 Promise vs async/await 对比

Promise 写法（链式）
function load() {
  return fetch('/api/user')
    .then(r => r.json())
    .then(user => fetch(`/api/orders?uid=${user.id}`))
    .then(r => r.json())
    .then(orders => console.log(orders))
    .catch(err => console.error(err));
}
async/await 写法（像同步）
async function load() {
  try {
    const user = await fetch('/api/user').then(r => r.json());
    const orders = await fetch(`/api/orders?uid=${user.id}`).then(r => r.json());
    console.log(orders);
  } catch(err) {
    console.error(err);
  }
}

两种写法功能完全一样，但 async/await 更易读、更接近人脑的思考方式。

13.4 await 的本质

⚠️ await 不是「等待」，而是「让出」

当 JS 引擎执行到 await 时，它会：
1. 暂停当前 async 函数的执行
2. 让出主线程，让其他代码（UI 渲染、事件处理等）可以继续执行
3. 等右边的 Promise 完成后，把结果返回，继续执行后面的代码

所以 await 不会阻塞页面！页面该滚动滚动、该点击点击。 它只是让当前函数内部的代码「暂停」了。
📌 本节总结 async function 声明一个异步函数。 await 等待右边的 Promise 完成并返回结果。 async/await 让异步代码看起来像同步代码，大大提升可读性。 本质还是 Promise，没有魔法。

第14节 · async 函数的返回值永远是 Promise

这是一个非常容易忽略的细节：async 函数无论 return 什么，返回值都是一个 Promise。

async function getNumber() {
  return 42;
}

// getNumber() 返回的不是 42，而是一个 fulfilled 的 Promise
const result = getNumber();
console.log(result); // Promise { <fulfilled>: 42 }

// 要拿到 42，需要 await 或 .then()
result.then(v => console.log(v)); // 42
const v = await getNumber();    // 42

14.1 面试题：async 函数 return 的值 vs throw

// return 值 → Promise fulfilled
async function 成功() {
  return 'OK';
}
// 等价于：return Promise.resolve('OK')

// throw 错误 → Promise rejected
async function 失败() {
  throw new Error('出错了');
}
// 等价于：return Promise.reject(new Error('出错了'))

// 不 return → Promise<undefined>
async function 空() {}
// 等价于：return Promise.resolve(undefined)
📌 本节总结 async 函数的返回值永远是 Promise。 return 值 → fulfilled 的 Promise，值为 return 的值。 throw Error → rejected 的 Promise，reason 为 Error。 不 return → fulfilled 的 Promise，值为 undefined。

第15节 · async/await 错误处理

在 Promise 中我们用 .catch() 处理错误。在 async/await 中，我们用回熟悉的 try/catch。

15.1 try / catch / finally

async function loadUserData() {
  try {
    // 尝试执行可能出错的代码
    const user = await fetch('/api/user').then(r => r.json());
    const orders = await fetch(`/api/orders?userId=${user.id}`).then(r => r.json());

    return { user, orders };
  } catch (err) {
    // await 的 Promise rejected 时，会跳到这里
    console.error('加载失败：', err);
    return { user: null, orders: [] }; // 返回默认值
  } finally {
    // 无论成功失败都执行
    hideLoadingSpinner();
  }
}

15.2 catch 不到的情况（常见坑）

// ⚠️ 坑1：await 忘记加
async function bad1() {
  try {
    const data = fetch('/api/data'); // ← 没有 await！fetch 返回 Promise
    console.log(data); // Promise { <pending> }
    // Promise 不会被 rejected 因为它还没执行，try/catch 捕获不到异步错误
  } catch (err) {
    // 进不来这里
  }
}

// ✅ 修正：加上 await
async function good1() {
  try {
    const data = await fetch('/api/data'); // ← 加上 await
  } catch (err) {
    // 能捕获到了！
  }
}

// ⚠️ 坑2：try 外面的 await
async function bad2() {
  try {
    const user = await fetch('/api/user');
  } catch (err) {
    // 只能捕获 fetch 的错误
  }
  const orders = await fetch('/api/orders'); // ← try 外面，捕获不到！
}

// ✅ 修正：所有 await 都放进 try
async function good2() {
  try {
    const user = await fetch('/api/user');
    const orders = await fetch('/api/orders');
  } catch (err) {
    // 两个都能捕获
  }
}
📌 本节总结 async/await 用 try/catch 处理错误，比 Promise 的 .catch() 更直观。 常见坑：
1. 忘记写 await（把 Promise 当成了普通值）
2. await 写在了 try 外面（catch 捕获不到）

第16节 · 并发 vs 串行（性能差距可达10倍！）

这是 async/await 最容易踩的坑：很多人写出了「串行」的代码而不自知，导致性能极差。

16.1 串行写法（性能差）

串行执行（一个完成再做下一个）： 时间线 ──────────────────────────────→ 请求A：�████████� (1秒) 请求B： �████████� (1秒) 请求C： �████████� (1秒) 总耗时：3 秒 ❌ 
// ❌ 错误写法：三个请求串行执行，总耗时 3 秒
async function loadSlow() {
  const user = await fetch('/api/user');        // 等 1 秒
  const orders = await fetch('/api/orders');     // 再等 1 秒
  const comments = await fetch('/api/comments'); // 再等 1 秒
  // 总耗时：3 秒
}

为什么是串行？ 因为 await 会暂停当前函数的执行，等 Promise 完成后才继续下一行。

16.2 并发写法（性能好）

并发执行（三个请求同时发出）： 时间线 ──────────────────────────────→ 请求A：�████████� (1秒) 请求B：�████████� (1秒) 请求C：�████████� (1秒) 总耗时：1 秒 ✅ 
// ✅ 方法1：Promise.all（推荐，最清晰）
async function loadFast1() {
  const [user, orders, comments] = await Promise.all([
    fetch('/api/user'),
    fetch('/api/orders'),
    fetch('/api/comments')
  ]);
  // 总耗时：1 秒（三个同时发）
}

// ✅ 方法2：先启动再 await
async function loadFast2() {
  const pUser = fetch('/api/user');     // 立刻发起，不等待
  const pOrders = fetch('/api/orders');  // 立刻发起，不等待
  const pComments = fetch('/api/comments'); // 立刻发起，不等待

  const user = await pUser;        // 等待结果（但请求已经在路上了）
  const orders = await pOrders;
  const comments = await pComments;
  // 总耗时：1 秒（三个同时发）
}

16.3 两种写法什么时候用？

场景应该用原因
三个请求互相独立（不依赖彼此的结果）并发（Promise.all）性能更好，节省时间
下一个请求依赖上一个的结果串行（await）必须先拿到上一个结果
不确定？看需求独立 → 并发
有依赖 → 串行		90% 的情况是独立的，应该并发
💡 经验法则 如果你发现自己的 async 函数里有连续 3 个以上的 await， 停下来想想：这些请求之间有没有依赖关系？ 如果没有，改成 Promise.all 并发执行，性能提升 N 倍。
📌 本节总结 await 会暂停函数执行，所以连续的 await 是串行的。 互不相关的请求应该用 Promise.all 并发执行。 有依赖关系的请求才需要串行（await 一个接一个）。

第17节 · 循环中的 async/await（超级大坑！）

17.1 for 循环：串行执行

// ✅ for...of 循环：await 会按预期工作（串行）
async function 串行请求(urls) {
  for (const url of urls) {
    const data = await fetch(url); // 等待完成后再下一次循环
    console.log(data);
  }
  // 输出：url1结果 → url2结果 → url3结果（按顺序）
}

17.2 forEach：不支持 await！（严重错误）

// ❌ 致命错误：forEach 里面 await 不会等待！
async function 错误写法(urls) {
  urls.forEach(async (url) => {    // ← 注意这个 async
    const data = await fetch(url);
    console.log(data);
  });


  }, 2000);
});

为什么 forEach 不支持 await？ 因为 forEach 的回调是一个普通函数（即使你加了 async），forEach 不会等待这个回调的 Promise 完成。它只是把每个回调放进任务队列就继续了。

17.3 正确的并发循环

// ✅ 方法1：map + Promise.all（并发执行）
async function 并发请求(urls) {
  const promises = urls.map(url => fetch(url)); // 同时发起所有请求
  const results = await Promise.all(promises); // 等全部完成
  return results;
}

// ✅ 方法2：for...of（串行，但保证顺序）
async function 串行请求有序(urls) {
  const results = [];
  for (const url of urls) {
    const data = await fetch(url);
    results.push(data);
  }
  return results; // 按 urls 的顺序返回
}

// ✅ 方法3：for await...of（遍历异步迭代器，ES2018）
async function 遍历异步(asyncIterable) {
  for await (const item of asyncIterable) {
    console.log(item);
  }
}
📌 本节总结 forEach 不支持 await，不要用！
需要并发 → map + Promise.all
需要串行 → for...of
遍历异步数据 → for await...of

第18节 · Generator 生成器函数

18.1 什么是 Generator？

Generator 是一种可以暂停和恢复的函数。普通函数一旦开始执行就会跑到结束，但 Generator 可以在中间暂停（yield），之后从暂停的地方继续。

// 声明：function*（注意星号）
function* 计数生成器() {
  yield 1;   // 第1次调用 next() → 暂停在这里，返回 1
  yield 2;   // 第2次调用 next() → 暂停在这里，返回 2
  yield 3;   // 第3次调用 next() → 暂停在这里，返回 3
  return '结束'; // 第4次调用 next() → 结束
}

// 调用 Generator 函数不会执行函数体，而是返回一个「迭代器」
const gen = 计数生成器();
// 此时函数体一行都没执行！

// 每次调用 next()，函数执行到下一个 yield 处暂停
console.log(gen.next()); // { value: 1, done: false }
console.log(gen.next()); // { value: 2, done: false }
console.log(gen.next()); // { value: 3, done: false }
console.log(gen.next()); // { value: '结束', done: true }
console.log(gen.next()); // { value: undefined, done: true }

18.2 Generator 的用途

用途说明
自定义迭代器让任何对象可以被 for...of 遍历
异步流程控制Redux-Saga 用 Generator 管理异步（async/await 出现前的方案）
惰性求值需要时才计算下一个值，节省内存
无限序列可以生成无限长的序列（如斐波那契数列）
// 实战：无限斐波那契数列
function* 斐波那契() {
  let a = 0, b = 1;
  while (true) {
    yield a;
    [a, b] = [b, a + b];
  }
}

const fib = 斐波那契();
fib.next(); // { value: 0 }
fib.next(); // { value: 1 }
fib.next(); // { value: 1 }
fib.next(); // { value: 2 }
fib.next(); // { value: 3 }
fib.next(); // { value: 5 }
// 永远不会结束（done 永远是 false）
� 本节总结 Generator = 可以暂停的函数。 function* 声明，yield 暂停，next() 恢复。 在 async/await 时代，Generator 主要用于自定义迭代器和 Redux-Saga。 日常异步编程用 async/await 就够了。

第19节 · 实战模式1：超时控制

场景：网络请求如果 5 秒还没返回，就报超时错误，不再等待。

/**
 * 给任意 Promise 加上超时控制
 * * @param {Promise} promise - 要执行的异步操作
 * @param {number} ms - 超时时间（毫秒），默认 5000
 * @returns {Promise} - 在超时时间内完成则返回结果，否则抛出超时错误
 */
function withTimeout(promise, ms = 5000) {
  // 创建一个"超时 Promise"：ms 毫秒后自动 rejected
  const timeout = new Promise((_, reject) => {
    setTimeout(() => {
      reject(new Error(`请求超时（超过 ${ms}ms）`));
    }, ms);
  });

  // 让"原 Promise"和"超时 Promise"赛跑
  // 谁先完成用谁的结果
  return Promise.race([promise, timeout]);
}

// 使用示例
async function loadData() {
  try {
    const data = await withTimeout(
      fetch('/api/slow-data').then(r => r.json()),
      3000 // 3秒超时
    );
    console.log('数据：', data);
  } catch (err) {
    if (err.message.includes('超时')) {
      console.log('请求超时，请重试');
    } else {
      console.log('请求失败：', err);
    }
  }
}
� 生活类比 你叫了一份外卖，跟平台说「30分钟没送到就自动退款」。 这里有两个「Promise」在赛跑：外卖送达 vs 30分钟倒计时。 哪个先发生，就执行对应的逻辑。

第20节 · 实战模式2：自动重试（指数退避）

场景：网络请求失败了，自动重试 3 次，每次等待时间翻倍（1秒 → 2秒 → 4秒）。

/**
 * 自动重试函数（指数退避策略）
 * * @param {Function} fn - 要重试的异步函数
 * @param {number} maxRetries - 最大重试次数，默认 3
 * @param {number} baseDelay - 基础延迟（毫秒），默认 1000
 */
async function retry(fn, maxRetries = 3, baseDelay = 1000) {
  for (let attempt = 0; attempt < maxRetries; attempt++) {
    try {
      // 尝试执行
      return await fn();
    } catch (err) {
      // 如果是最后一次尝试，不再重试，直接抛出错误
      if (attempt === maxRetries - 1) {
        throw err;
      }

      // 计算等待时间：1s, 2s, 4s, 8s...（指数退避）
      const delay = baseDelay * 2 ** attempt;

      console.log(`第 ${attempt + 1} 次失败，${delay}ms 后重试...`);

      // 等待 delay 毫秒后再重试
      await new Promise(resolve => setTimeout(resolve, delay));
    }
  }
}

// 使用示例
async function loadWithRetry() {
  const data = await retry(
    () => fetch('/api/unstable').then(r => r.json()),
    3,    // 最多重试3次
    1000  // 基础延迟1秒
  );
  return data;
}
� 为什么用「指数退避」？ 如果服务挂了，立刻重试 → 再失败 → 立刻重试 → 会给服务器更大压力。 指数退避让重试间隔越来越长（1s → 2s → 4s → 8s），给服务器恢复的时间。 这是业界标准做法（gRPC、AWS SDK 等都用指数退避）。

第21节 · 实战模式3：并发限制

场景：有 100 个请求要发，但浏览器最多同时 6 个并发请求。需要控制同时进行的请求数量。

/**
 * 并发池：限制同时执行的异步任务数量
 * * @param {Function[]} tasks - 任务数组（每个任务是一个返回 Promise 的函数）
 * @param {number} limit - 最大并发数
 */
async function pool(tasks, limit) {
  const results = [];
  const executing = new Set(); // 正在执行的任务

  for (const task of tasks) {
    // 启动一个任务
    const p = task().then(r => {
      executing.delete(p); // 完成后从执行集合中移除
      return r;
    });

    results.push(p);
    executing.add(p);

    // 如果正在执行的任务数达到上限，等最快的那个完成
    if (executing.size >= limit) {
      await Promise.race(executing);
    }
  }

  // 等所有任务完成
  return await Promise.all(results);
}

// 使用示例：100张图片，最多同时下载6张
const urls = Array.from({ length: 100 }, (_, i) => `https://example.com/img/${i}.jpg`);
const tasks = urls.map(url => () => fetch(url).then(r => r.blob()));

pool(tasks, 6).then(blobs => {
  console.log(`下载完成，共 ${blobs.length} 张图片`);
});

第22节 · 实战模式4：请求缓存

场景：同一个 URL 不要重复请求，第一次请求后缓存结果，后续直接返回缓存。

/**
 * 带缓存的 fetch
 * * @param {string} url - 请求地址
 * @param {number} ttl - 缓存有效期（毫秒），默认 60000（1分钟）
 */
const cache = new Map();

async function cachedFetch(url, ttl = 60000) {
  // 检查缓存是否存在且未过期
  if (cache.has(url)) {
    const { data, expire } = cache.get(url);
    if (Date.now() < expire) {
      console.log('✅ 缓存命中：', url);
      return data;
    } else {
      cache.delete(url); // 过期了，删掉
    }
  {

  // 缓存不存在或已过期，发起真实请求
  console.log('� 发起请求：', url);
  const data = await fetch(url).then(r => r.json());

  // 存入缓存
  cache.set(url, {
    data,
    expire: Date.now() + ttl
  });

  return data;
}

// 使用示例
await cachedFetch('/api/user'); // 发起请求
await cachedFetch('/api/user'); // 命中缓存（不发起请求）
await cachedFetch('/api/user', 5000); // 5秒缓存

第23节 · 实战模式5：取消请求

场景：用户快速切换 Tab 时，取消上一个 Tab 还在进行的网络请求。

/**
 * 使用 AbortController 取消请求
 * * 场景：搜索框输入时，每次输入都发请求，但只保留最后一次的结果
 */
class SearchService {
  constructor() {
    this.controller = null;
  {

  async search(keyword) {
    // 如果之前有正在进行的请求，取消它
    if (this.controller) {
      this.controller.abort();
    {

    // 创建新的控制器
    this.controller = new AbortController();

    try {
      const res = await fetch(`/api/search?q=${keyword}`, {
        signal: this.controller.signal // 绑定取消信号
      });
      const data = await res.json();
      return data;
    } catch (err) {
      if (err.name === 'AbortError') {
        // 这是被我们主动取消的，不是真正的错误
        console.log('请求被取消');
        return null;
      }
      // 真正的网络错误
      throw err;
    }
  }
}

// 用户快速输入 "vue"

searchService.search('vu');   // 发起请求 → 很快被取消
searchService.search('vue');  // 发起请求 → 这是最后一次，不会被取消
� 本节总结 AbortController 是浏览器提供的取消异步操作的标准 API。 通过 signal 属性把「取消信号」传给 fetch。 调用 controller.abort() 后，绑定了该 signal 的 fetch 会抛出 AbortError。 这是搜索框防抖、Tab 切换取消请求的标准做法。

面试高频问题速答

问题答案
Promise 有几种状态？3 种：pending、fulfilled、rejected。状态只能改变一次，不可逆。
Promise.all 和 Promise.race 的区别？all：全部成功才成功；race：谁先完成用谁。
async 函数的返回值是什么？永远是 Promise。return 值 → fulfilled 的 Promise。
await 会阻塞主线程吗？不会！await 只暂停当前 async 函数，主线程继续执行其他代码。
forEach 里可以用 await 吗？不能！forEach 不会等待 Promise。用 for...of 或 map + Promise.all。
catch 之后链会恢复吗？会！catch 返回新的 Promise，后续 then 正常执行。
